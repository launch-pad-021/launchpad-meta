# 03 — Conventions (all services, all languages)

This document is the source for the `launchpad-conventions` repo. Every service MUST follow it; reviewers check against it.

## 1. Identifiers and time
- Entity IDs: **UUIDv7**, generated by Postgres `uuidv7()` on insert or by the service (`google/uuid` NewV7, Rust `uuid` v7, Python `uuid6`/stdlib where available). Rendered lowercase canonical form.
- Event IDs: UUIDv7. Short deploy ID in hostnames: first 8 hex chars of the deployment UUID's random part (`d-<8hex>`); collisions checked by `router`.
- Time: UTC everywhere. JSON/RFC 3339 with milliseconds (`2026-11-21T10:00:00.123Z`); protobuf `google.protobuf.Timestamp`; ClickHouse `DateTime64(3, 'UTC')`.
- Slugs: lowercase `[a-z0-9-]`, 1–40 chars, no leading/trailing `-`. App names are slugs. Branch slug: lowercase, non-alnum → `-`, collapse repeats, max 30 chars.

## 2. Ports, health, metrics
| Port | Purpose |
|---|---|
| 9000 | gRPC (if the service has a gRPC API) |
| 8080 | HTTP: `/healthz`, `/readyz`, `/metrics`, and public HTTP for gateway/scm/ingest |

- `/healthz`: 200 when the process is alive. No dependency checks.
- `/readyz`: 200 only when required dependencies (DB, broker, downstream gRPC listed in the service spec) are reachable; JSON body `{"status":"ok|degraded|down","checks":{"postgres":"ok",...}}`.
- `/metrics`: Prometheus text format. Not exposed through Traefik.

## 3. Configuration
- 12-factor: configuration via environment variables only; secrets via files mounted at `/run/secrets/<name>` (Docker secrets) and referenced by `*_FILE` variables.
- Naming: `LP_<AREA>_<NAME>` (e.g. `LP_PG_DSN_FILE`, `LP_KAFKA_BROKERS`, `LP_LOG_LEVEL`).
- Common variables every service reads:

| Variable | Example | Meaning |
|---|---|---|
| `LP_SERVICE_NAME` | `deployer` | Used in logs, traces, metrics |
| `LP_ENV` | `prod` / `dev` / `test` | |
| `LP_LOG_LEVEL` | `info` | debug/info/warn/error |
| `LP_KAFKA_BROKERS` | `redpanda:9092` | |
| `LP_OTEL_ENDPOINT` | `http://otel-collector:4317` | OTLP gRPC |
| `LP_IDENTITY_ADDR` | `identity:9000` | For JWKS + service tokens |
| `LP_SERVICE_SECRET_FILE` | `/run/secrets/svc_deployer` | Service credential for `IssueServiceToken` |
| `LP_BASE_DOMAIN` | `example.com` | |

- Services MUST fail fast at startup on missing/invalid config, logging which variable is wrong (never its value).

## 4. Errors
- gRPC: use standard status codes. Mapping the gateway applies to HTTP:

| gRPC | HTTP | When |
|---|---|---|
| INVALID_ARGUMENT | 400 | Validation failed (include field violations via `google.rpc.BadRequest`) |
| UNAUTHENTICATED | 401 | Missing/invalid credential |
| PERMISSION_DENIED | 403 | Authenticated but not allowed |
| NOT_FOUND | 404 | |
| ALREADY_EXISTS | 409 | Unique constraint |
| FAILED_PRECONDITION | 409 | Wrong state (e.g. rollback of a failed deploy) |
| ABORTED | 409 | Concurrency conflict (retryable by client) |
| RESOURCE_EXHAUSTED | 429 | Rate limited |
| UNAVAILABLE / DEADLINE_EXCEEDED | 503 / 504 | Retryable |
| INTERNAL / UNKNOWN | 500 | Bug; never leak internals |

- HTTP error body: RFC 9457 `application/problem+json`: `{"type":"https://launchpad.dev/errors/<code>","title":"...","status":409,"detail":"...","instance":"/apps/...","request_id":"..."}`. `type` codes are kebab-case and stable.
- Never put secrets, tokens, env values, SQL or stack traces in error messages returned to clients.

## 5. Retries, timeouts, idempotency
- Client retries only on UNAVAILABLE/DEADLINE_EXCEEDED/ABORTED, max 3, exponential backoff with jitter (100 ms base, 2 s cap).
- Every mutating public REST call accepts `Idempotency-Key` (UUID); gateway stores key → response for 24 h in Redis.
- gRPC mutations that can be retried by the saga carry an explicit idempotency field (`deployment_id`, `request_id`) and MUST be idempotent server-side (e.g. `StartContainer` with an existing `deployment_id` returns the existing container).

## 6. Events
### 6.1 Envelope (JSON, UTF-8)
```json
{
  "id": "0193f1c2-....",            // UUIDv7, unique per event
  "type": "deployment.live.v1",      // <domain>.<event>.v<major>
  "source": "deployer",              // producing service
  "time": "2026-11-21T10:00:00.123Z",
  "subject": "app/<app_id>",         // optional
  "traceparent": "00-<trace>-<span>-01",
  "data": { ... }                    // validated by contracts/events/<type>.schema.json
}
```
- Kafka record key = `app_id`. Exceptions: `lp.scm` events are keyed by `repo_full_name` (scm doesn't know app IDs); `lp.identity` by token id. Header `ce-type` duplicates `type` for filtering.
- Event types are versioned; additive changes keep the version; breaking changes create `.v2` and producers emit both until consumers migrate.
- Events MUST NOT contain secrets, env var values, tokens, IPs (except `insights.event` before processing), or full user agents outside Insights.

### 6.2 Topics
| Topic | Partitions | Retention | Events |
|---|---|---|---|
| `lp.identity` | 1 | 7 d | token.revoked |
| `lp.scm` | 3 | 7 d | scm.push, scm.branch_deleted |
| `lp.projects` | 3 | 30 d (compaction off) | app.created, app.updated, app.deleted, env.changed |
| `lp.deployments` | 3 | 30 d | deployment.status_changed, deployment.live, deployment.failed, build.requested |
| `lp.builds` | 3 | 7 d | build.started, build.completed, build.failed |
| `lp.build-logs` | 3 | 7 d | build.log |
| `lp.runtime` | 3 | 3 d | runtime.log, container.exited |
| `lp.routes` | 1 | 7 d | route.changed |
| `lp.insights` | 1 | 30 d | vitals.regressed |
| `events.raw` | 6 | 3 d | insights.event |
| `events.dlq` | 1 | 14 d | dlq (any failed message) |

Topics are created by `launchpad-infra` (`rpk topic create`), never auto-created (`auto_create_topics_enabled=false`).

### 6.3 Consumers
- Consumer group = `<service>` (or `<service>-<purpose>`).
- At-least-once: commit offsets **after** the side effect succeeds.
- Idempotency: record `event.id` in `processed_events` (same transaction as the effect, for DB-backed services) or check natural idempotency.
- Poison messages: after 5 failed attempts, publish to `events.dlq` with the original topic/partition/offset/error, then commit. DLQ depth is alerted.

### 6.4 Outbox relay
Runs in-process: polls `outbox WHERE published_at IS NULL ORDER BY created_at LIMIT 100` every 200 ms (and on `LISTEN/NOTIFY outbox`), produces with idempotent producer and `acks=all`, sets `published_at`. Rows older than 7 days and published are deleted nightly.

## 7. Observability
- **Traces:** OTel SDK; propagate W3C `traceparent` via gRPC metadata, HTTP headers and event envelopes. Span names: `<rpc method>` / `HTTP <METHOD> <route>` / `consume <topic>` / `produce <topic>`.
- **Logs:** JSON lines to stdout. Required fields: `ts`, `level`, `msg`, `service`, `trace_id`, `span_id` (when in a span). Optional: `app_id`, `deployment_id`, `request_id`, `event_id`, `error`. Never log secrets, tokens, env values, full request bodies, IPs (Insights).
- **Metrics:** prefix `lp_<service>_`. Required in every service: `lp_<svc>_build_info{version}`, gRPC server/client histograms (`..._grpc_server_duration_seconds{method,code}`), HTTP histograms, `..._consumer_lag{topic}`, `..._outbox_pending`, `..._events_processed_total{type,result}`.

## 8. Security defaults
- Containers run as non-root, read-only root FS where possible, `no-new-privileges`, dropped capabilities.
- Inputs validated at the edge (gateway, scm, ingest) and again in the owning service.
- SQL only via parameterized queries / sqlc; ClickHouse queries parameterized (`{name:Type}`).
- Secrets never in env vars directly (use `*_FILE`), never in logs/events/errors.

## 9. Repositories
- Name: `launchpad-<service>`. Default branch `main`. One deployable per repo.
- Layout (any language):
```
<src dir>/                  service code (Go: cmd/<svc>/ + internal/; Rust: src/; Python: src/lp_<svc>/; TS: src/)
migrations/                 if the service owns Postgres tables (goose for Go, node-pg-migrate for TS)
test/                       integration tests (unit tests live next to code per language norms)
Dockerfile                  multi-stage, non-root, arm64+amd64
CLAUDE.md  AGENTS.md  README.md  CODEOWNERS  renovate.json
.github/workflows/          ci.yml, agent.yml, release-please.yml (thin callers)
```
- README MUST list: purpose, owned data, gRPC API, events in/out, config variables, how to run tests.

## 10. Git
- Branches: `agent/<issue-number>-<slug>` (agents), `dev/<slug>` (developer).
- Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `ci:`; `!` for breaking). Required by release-please.
- Squash merge only; linear history; no force-push to `main`.
- PR title = Conventional Commit; PR body uses the template in `bootstrap/templates/PULL_REQUEST_TEMPLATE.md`.

## 11. Dockerfiles
- Multi-stage; final stage `gcr.io/distroless/static` (Go/Rust static), `python:3.14-slim`, or `node:26-slim`.
- `USER 65532:65532` (or a named non-root user). `HEALTHCHECK` not used (compose healthchecks instead).
- Pin base images by digest (Renovate updates digests).

## 12. Definition of Done (every issue)
1. Acceptance criteria each have linked evidence (test or CI log).
2. Unit + integration tests added/updated; CI green.
3. Conventions in this file followed; lints clean.
4. Docs updated (README, service spec if behavior changed via a spec PR, ADR if a decision was made).
5. Observability: spans, metrics, logs for new paths.
6. Security checklist items for touched areas satisfied.
7. Reviewers approved; merged; deployed; post-deploy verification passed.
